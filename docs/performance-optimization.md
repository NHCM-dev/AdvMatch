# 撮合与合约性能优化

## 已实现的改动

| 路径 | 实现 |
| --- | --- |
| 已有价格档 | 先从价格哈希索引定位，命中后直接入 FIFO；新增价格档才查有序树 |
| 仓位和合约参与者 | BigAllocs 保存稳定对象，DenseMap 保存 ID 到指针的索引；账户共享 Position 池 |
| 订单与仓位历史 | 显式确认归档后释放对象，复用池中的槽位；订单和仓位 ID 不复用 |
| 标记价、资金费、交割 | 复用预检查工作区、账户净额索引和容量；整批成功才提交余额与仓位变化 |
| FOK | 复用影子账户、仓位、参与者和订单池；失败不会改变实际持仓和余额 |
| 合约成交 | maker/taker 共用已校验成交金额；余额只定位一次，生成凭据后统一提交 |
| 现货成交 | 合并准备双方资产变动，扣款先于入账；保留现货自成交语义 |
| 价格保护 | 缓存当前标记价和价格带配置对应的整数上下限 |
| 强平 | 自动重试按流动性/标记价/保险金等版本变化触发；同轮全仓按账户与抵押资产合并处理 |
| 消费队列 | 分批发布消费进度；响应只唤醒已登记等待的请求，轮询响应不额外通知 |

所有修改状态的方法仍须在同一消费线程调用，工作区不支持并发或回调重入。资金费率和交割保持整批预检查；资源分配失败属于引擎资源故障，不能当作普通业务拒单继续交易。

## 历史归档

实现 `HistorySink`，在消费线程的维护时段调用：

```cpp
// historyStore 是上层实现的 HistorySink，必须先复制或接收历史值。
const HistoryArchiveResult result = matching.archiveHistory(historyStore, 1024);
```

`archiveOrder(const BasicOrder&)` 和 `archivePosition(const Position&)` 返回 true 表示接收成功，允许引擎删除查询记录并回收对象；返回 false 表示保留并以后重试。回调必须 noexcept，不能重入引擎，也不能保存参数的引用或指针。

归档只处理终结且没有余额预留/链表链接的订单，以及已关闭且没有挂单或留存订单引用的仓位。订单释放会减少参与者引用计数，仓位可能在之后的扫描中回收。参数是扫描预算，不是必须归档的数量；返回结果包含实际扫描和归档数量。预算为 1 时交替扫描订单与仓位，避免仓位饥饿。

默认不自动归档。成功归档后，`queryOrder` / `queryPosition` 不再返回该记录，外部已借用的仓位指针失效。历史查询应走上层 HistorySink 对应的历史存储。

对象池保留高水位容量供后续复用，不保证进程 RSS 立即降低。OrderId 的直接数组索引保留空槽，每个历史 ID 仍占一个指针大小；这是保持最坏 O(1) 查询的当前折中。扫描稀疏历史索引可能需要多轮。归档接口本身不提供 WAL、崩溃恢复或持久性承诺，接收成功的标准由上层定义。

## 队列与响应

```cpp
consumer.start(32);     // 自动消费进度批量：min(32, max(1, ringSize / 4))
consumer.start(128, 8); // 另一个实例：显式每 8 条发布消费进度
```

每个实例只能 start 一次。显式批量必须不大于 ringSize，0 表示自动。消费到当前已发布序列的末尾一定刷新进度，再等待新命令，因此 ringSize 为 1 也不会因批量刷新发生死锁。消费进度批量与生产端 postBatch 的发布批量是不同参数。

响应在完成后立即可见；`RequestTicket::get()` 登记 Waiting 状态后才等待。消费线程原子交换完成状态，并只通知 Waiting，避免“先完成、后等待”造成漏唤醒。`isReady()` 的轮询路径直接观察完成状态。

ResponseSlot 仍由生产者拥有，必须保留到 ticket 被 get 消费；取得结果后才能复用。同一个 ticket 不允许多个线程同时 get，也不能把未消费 ticket 对应的 slot 提前销毁。派生 consumer 的析构函数仍须调用 stopBeforeDerivedDestruction。

## 余额凭据与指针安全

`Account::captureBalance` 返回不暴露地址的快照，`prepareBalanceChange` 校验余额上下限并生成 BalanceUpdate，`commitBalanceChange` 提交。增加/删除余额、从内联 10 项迁移到哈希容器等结构修改会更新 generation，提交前先检查 generation，避免解引用已失效地址。普通余额变动则通过预期旧值识别过期更新。

过期、跨账户或重复的非零更新返回 StaleUpdate。凭据仅用于同一消费线程中的短事务，不能长期存储，也不提供线程同步。对多个账户必须先完成所有准备，再按安全顺序提交；不能在中间穿插外部余额修改。

SpotSettleEngine 现在显式接收 `SpotAccountLedger&`，因为现货双方结算由具体账本集中执行。已有传入 SpotAccountLedger 的调用保持兼容；把它仅作为 AccountLedger 引用传入的外部代码需要保留具体类型。

## 同机压测

2026-10-07，Windows / AMD Ryzen 7 7435HS（8 核 16 线程），MSYS2 UCRT64 Release，顺序执行三次。优化前和优化后使用同一命令及默认参数：

```powershell
cmake --preset release
cmake --build --preset release
ctest --preset release
1..3 | ForEach-Object { .\build\release\advmatch_perpetual_benchmark.exe --orders 1000000 --warmup 1000 }
```

默认参数：1024 用户、1 产品、4 producers、ringSize 32、batch 256、publish 8、逐仓杠杆 10、maker 100 / taker 500 ppm；预加载 100 万卖单，提交 100 万买单，形成 200 万仓位。延迟每 1024 条采样，从命令构造时到消费线程执行完成，包含提交、排队及撮合，不包含生产者取回响应的耗时。六次运行均 validation=passed。

| 阶段/运行 | 成交 TPS | p50 μs | p99 μs | 标记价秒 | 资金费秒 | 资金费仓位/秒 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 优化前 1 | 393945 | 1210.2 | 2948.4 | 0.468 | 1.101 | 1816467 |
| 优化前 2 | 410788 | 1180.0 | 3071.8 | 0.456 | 1.010 | 1979486 |
| 优化前 3 | 434309 | 1113.2 | 2771.8 | 0.436 | 1.033 | 1936559 |
| 优化后 1 | 512312 | 958.2 | 2171.9 | 0.089 | 0.324 | 6164134 |
| 优化后 2 | 504236 | 971.4 | 2221.0 | 0.095 | 0.346 | 5779258 |
| 优化后 3 | 522443 | 939.6 | 2038.2 | 0.087 | 0.207 | 9669917 |

分别取各指标中位数：成交 TPS 提升约 24.7%，p50 降低 18.8%，p99 降低 26.3%；标记价耗时降低约 80.5%，资金费仓位吞吐约为原来的 3.18 倍。这是本机开仓场景的结果，不能代表全部规模、强平密集或跨产品全仓场景。资金费结果波动明显，生产评估仍应测持续运行和尾延迟。

## 复杂度与验证

OrderId 直接索引最坏 O(1)，ID/价格哈希查询平均 O(1)，已有价格档入队不查树。新价格档创建与最后节点删除仍涉及 O(log L) 有序树；撮合与实际成交/取消数量相关。标记价、资金费、交割仍是 O(P)，FOK 和全仓强平仍与涉及的订单/仓位数量有关。归档最多扫描给定预算，回调自身耗时由调用方控制。

新增 `advmatch_optimization_tests` 覆盖：跨池扩容地址稳定、24000 订单/12000 仓位归档、拒绝归档/预算 1/ID 不复用、余额内联迁移和失效凭据、现货自成交、FOK 拒绝与后续成功共用工作区、重复资金费周期以及 ringSize 1/2/32/128 下双生产者、失败响应和 void 响应复用。

Release 与 Debug 各 12 项 CTest 通过。测试命令：

```powershell
cmake --build --preset release
ctest --preset release --timeout 30
cmake --build --preset debug
ctest --preset debug --timeout 30
```
